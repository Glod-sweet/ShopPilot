# ShopPilot

> 基于 Agent 的智能导购系统 · Vue3 + Spring Boot 3.5 + Python LangChain / LangGraph

传统电商的关键词搜索要求用户先想清楚「买什么」；ShopPilot 把这一步交给 Agent：用户只表达模糊意图，系统完成**需求澄清 → 混合检索 → 场景化推荐 → 理由解释**，全程流式返回。

三端职责互不越界：Vue3 负责对话与卡片渲染，Spring Boot 是唯一有状态层（鉴权、会话、商品、订单），Python Agent 是无状态编排层（意图、检索、工具调用）。请求以 SSE 三端流式透传，商品卡片在工具返回的瞬间就推给前端，不等模型把话说完。

## 一次请求发生了什么

| 阶段 | 动作 | 关键点 |
|---|---|---|
| ① 槽位判定 | 正则 + 词表抽出品类 / 预算 / 场景 | 必填缺失就**直接追问**，不进模型也不检索——省掉一次完整调用，也避免模型「先搜一堆再反问」 |
| ② 上下文装配 | 识图转文本 · 用户画像 · 导购知识 RAG · 会话记忆 | 图片只过一次 VL 模型转成文本，后续轮次复用，成本降一个数量级 |
| ③ ReAct 编排 | 模型自主决定调检索 / 详情 / 比价 / 历史订单 | 穿过上下文裁剪、工具重试、审计三层中间件；Agent 只持有 4 个**只读**工具，加购下单一律交回用户在界面上确认 |
| ④ 流式返回 | token / tool_call / product_card 事件逐条下发 | Python → Java（WebFlux Flux）→ 前端逐字渲染，中间态可感知 |

## 要解决的问题

传统电商是「人找货」：用户必须自己想清楚要什么、自己拆关键词、自己比对参数。但真实购物场景里，用户往往只有一个模糊的意图——「想给女朋友买个生日礼物，300 以内」——却不知道对应什么商品、该搜什么词。

ShopPilot 把这段翻译和决策的工作交给 Agent：用户只需表达意图，Agent 负责理解、筛选、对比、解释理由；真正涉及资金与库存的写操作，仍由用户自己在界面上确认执行。

## 核心能力

| 能力 | 说明 |
|---|---|
| 场景化选品 | 把抽象意图（生日礼物、露营装备）映射到具体品类，结合预算与场景排序 |
| 多品对比 | 针对具体使用场景做取舍，而非罗列参数表 |
| 槽位澄清 | 需求不全时主动追问，信息齐备才执行检索 |
| 推荐理由 | 由模型针对当前这句话重写理由，而非复用语对所有用户都一样的卖点文案 |
| 交易代办 | 识别「再来一单」类意图并查回历史订单，加购下单交由用户在界面确认 |

## 架构

```
Vue3 (5173) ──HTTP/SSE──▶ Java (8080) ──HTTP/SSE──▶ Python Agent (8000)
                              ▲                            │
                              └────── 工具反向调用 ──────────┘
```

- **Vue3 前端**：对话界面、商品卡片渲染、SSE 流式输出、会话历史
- **Java 后端**：唯一对外入口，鉴权、会话持久化、商品与订单业务、混合检索与重排序、交易一致性
- **Python Agent**：无状态服务，意图识别、槽位抽取、导购知识 RAG、LangGraph ReAct 编排、工具调用

职责边界：Java 是唯一有状态层，Python 不碰数据库、不解析 JWT。数据库权限不下放。

## 技术要点

- **混合检索**：先结构化过滤（上架/库存/价格/品类）拿候选，再在候选集内算余弦并做 min-max 归一化，最后按语义 0.45 + 场景 0.30 + 评分销量 0.25 加权重排。之所以不是「先向量召回」：MySQL 社区版无向量索引，先召回等于全表扫描，实测反而更慢
- **双 RAG**：商品检索走 MySQL 向量列（应用层算余弦），导购知识走进程内向量库（向量 0.7 + 关键词 IDF 0.3 融合），两类问题分流
- **会话记忆**：Redis 存最近 N 轮原文 + 超阈值自动摘要压缩，上下文不无限膨胀（Redis 不可用时降级进程内存）
- **上下文工程**：中间件按条数 + 字符数双预算裁剪，且按槽位填充度动态调整预算；保证 tool_call 与 tool_result 不被切断
- **多模态**：图片先经 VL 模型转文本描述，后续轮次复用，避免重复传图
- **多品对比**：用户可勾选 2~5 件商品，Agent 并发拉详情后按质量/性价比/适配场景三维度比较并给结论
- **MCP 接入**：Tavily 官方 MCP server（stdio）提供联网检索，站内商品库覆盖不到时兜底
- **槽位前置判定**：规则 + 词表抽取品类/预算/场景，必填缺失直接产出 `slot_ask`，不进 ReAct 循环；并放行「再来一单」「带图」「回指追问」等不该打断的场景
- **SSE 流式透传**：Python → Java（WebFlux Flux，全程不 collectList）→ 前端逐字渲染，商品卡片在工具返回瞬间即推送
- **工具反向调用**：Python 通过带内部令牌的 `/internal/*` 接口回调 Java，读多写少，写操作不向 Agent 开放

## 分阶段路线

| 阶段 | 交付 | 验收 |
|---|---|---|
| P1 | 单轮对话 + 向量检索 + 商品卡片 | 说「300 以内的蓝牙耳机」能出真实商品卡片 |
| P2 | 结构化过滤 + 槽位追问 | 「买礼物」会反问预算；「500 以内」不推 5000 的 |
| P3 | 交易工具（加购 / 再来一单） | 「再来一单」可查回历史订单；加购/下单未向 Agent 开放写工具，由用户在界面确认后走 Java 接口 |
| P4 | 多品对比 | 勾选 2~5 件，三维度比较并给出明确结论 |
| P5 | 流式 + 会话持久化 + 前端打磨 | 逐字输出，历史可回看 |

## 明确不做

商品管理后台、支付渠道对接、物流履约——复用已有电商项目。本项目只聚焦「对话式导购」这一层。
